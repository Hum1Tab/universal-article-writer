# 検証ノート — 2026-10-28（v3.1.0）

v3.1 で「残るリスク」として挙げた4点を、実行できる範囲で検証した記録である。
**測ったのは構造と挙動の一部であり、記事の品質ではない。**

## 0. 方法と限界（先に読む）

- 生成・ルーティング・採点はすべて同一モデル（別セッション）で行った。**独立した人間評価ではない。**
- 各条件の実行回数は 1 回。統計的な有意性は主張しない。
- heavy/light 各12件の 12/12 は、95% Wilson 下限で約0.76。点推定の完全一致を「完璧」と読まない。
- 監査スクリプトは構造のみを見る。意味内容・論証の強さは判定しない。
- ルーティング用のプロンプト集合は small-N（各24件）で、著者が作成したものと、別エージェントが生成したもの（held-out）の2種類を使った。
- 以下の結果は「この環境・このモデル・この課題」での観測であり、一般化しない。

再現コマンドは §5。

## 1. リスク1：description を狭めたことによる取りこぼし

### 1.1 方法

`evals/trigger-prompts.json`（著者作成、24件）と
`evals/trigger-prompts-heldout.json`（別エージェントが生成、24件）を用意した。
各24件は heavy 12件（証拠・因果・規範・設計判断）と light 12件（推敲・整形・要約・ブレスト）からなる。
ルーターには description と依頼だけを与え、LOAD / SKIP を返させた。
old / new のどちらかは伏せ、別セッションで実行した。

### 1.2 結果

| プロンプト集合 | description | heavy の LOAD | light の LOAD | recall | specificity |
|---|---|---|---|---|---|
| 著者作成 | old（v3.0.1） | 11/12 | 2/12 | 0.92 | 0.83 |
| 著者作成 | new（v3.1） | 12/12 | 0/12 | 1.00 | 1.00 |
| held-out | old（v3.0.1） | 12/12 | 0/12 | 1.00 | 1.00 |
| held-out | new（v3.1） | 12/12 | 0/12 | 1.00 | 1.00 |
| held-out | placebo（料理スキル） | 0/12 | 0/12 | 0.00 | 1.00 |

- 著者作成の集合で old が誤って LOAD したのは「ブログの見出しを5つ」「この文章を読みやすくして」。
  どちらも old description が列挙していた字面のトリガー（「見出しを強くして」「読みやすくして」）に一致する。
- old が取りこぼしたのは「設計案AとBのどちらを採るか、撤退条件付きで決定メモを書いて」。
  old description に design decision の記述がないため。
- **held-out では old と new が同じ判定になった。** 字面のトリガーを含まない依頼では、old の広さは誤発火を生まなかった。
- placebo（無関係な料理スキル）は 24件すべて SKIP。ルーターが description を無視して課題の難易度だけで判定しているわけではないことを確認した。

### 1.3 解釈

- 「old は推敲で必ず発火する」という GROK の指摘は、**字面のトリガーが使われたときに限り**再現した。
  これは小さなことではない。ユーザーはまさにその言い方をするからである。
- ただし「new が一貫して優れる」とは言えない。held-out では差がなかった。
- 著者作成の集合は v3.1 の設計後に作ったため、new に有利な語彙が混じる可能性がある。
  held-out はその対策として、どちらの description も見ていない別エージェントに生成させた。
- 取りこぼし（heavy の SKIP）は、new では 2 集合とも 0 件。old は設計判断の1件を落とした。
  **この範囲では、狭めたことによる recall の低下は観測されなかった。**

**残る不確実性**：実ホストのルーターは、この実験のルーターと異なる。プロンプト集合も24件ずつで小さい。
「字面のトリガーを含む依頼がどれくらいの頻度で来るか」は測定していない。

## 2. リスク2：references を読まない／読めない

### 2.1 静的検査

`check_consistency.py` に、フェーズごとの出口条件と詳細ファイルの対応検査を追加した（36チェックの一部）。

- 全フェーズに、観測可能な出口条件がある。
- 全フェーズに、実在する詳細ファイルが紐づいている。
- 参照が読めない場合の縮退（「本文の規則と出口条件だけで進み、省略を明記する」）が本文にある。
- 出力契約（`article.md`, `decision-memo.md`, `sources.csv`, `claims.csv`, `dossier.md`, `logic-report.md`）と G0–G7 の順序も検査する。

### 2.2 挙動（A/B）

同じ課題（E01 の引用検証バリアント）を3条件で実行した。

| 条件 | 読んだ references | 読んだ assets | 出力ファイル | 監査 |
|---|---|---|---|---|
| old | `japanese-editing.md` のみ | 0 | 5/5 | READY / PASS / PASS |
| new | `citation-and-provenance.md`, `japanese-editing.md` | 0 | 5/5 | READY / PASS / PASS |
| new-blind（参照禁止） | 0 | 0 | 5/5 | READY / PASS / PASS |

- **old でも references は1本しか読まれなかった。** 「本体が手順書だから参照が読まれない」というより、
  参照は元々あまり読まれていない。v3.1 の変更で読まれ方が悪化した証拠は、この1回では出ていない。
- **参照を禁止した new-blind でも、5つの成果物が揃い、監査は READY/PASS だった。**
  足りない手順（ACH、規範理論2つ、7原則の明示適用、6役の独立レビューなど）は `dossier.md` に列挙された。
  これは「本文だけで最低限は動く」という v3.1 の縮退契約が、少なくとも構造的には機能したことを示す。
- ただし new-blind の自己判定は **CONDITIONAL**（全出典が `partial`）であり、監査スクリプトの READY より厳しい。
  判定基準の差であり、失敗ではない。品質（論証の深さ）は明らかに落ちる。

**残る不確実性**：n=1。blind 条件は監査スクリプトを読んで自己点検しており、参照の代わりに検査工具を使っている。
「参照なしでも品質が保たれる」とは言えない。言えるのは「構造と監査は通る」までである。

## 3. リスク3：ゲート遵守の低下

### 3.1 方法

E01 の課題を old / new / new-blind の3条件で実行し、**生成された成果物を、生成したモデルとは別に、決定論的な監査スクリプトで採点した**。
自己採点ではなく、`audit_article.py` / `argument_lint.py` / `verify_sources.py` の出力を使った。

### 3.2 結果

| 条件 | Readiness | Critical/Major/Minor | argument-lint | source-report | 構造スコア |
|---|---|---|---|---|---|
| old | READY | 0 / 0 / 3 | PASS | PASS | 6/6 |
| new | READY | 0 / 0 / 3 | PASS | PASS | 6/6 |
| new-blind | READY | 0 / 0 / 3 | PASS | PASS | 6/6 |

構造スコアは、5ファイルの存在、3つ以上の出典マーカー、3件以上の主張、荷重主張の falsifier、未確認の可視性、TODO の不在の6項目。

- 3条件とも、同じ Minor（`citation-partial-source` 3件）で、Critical/Major は 0。
- 出典マーカー、claims.csv の列、falsifier の付与に差はなかった。
- 文字数は old 773字、new 614字、blind 795字（いずれも参考文献を除く）。new は指定範囲の下限に近い。

### 3.3 解釈

この1課題では、slim 化による**構造的なゲート遵守の低下は観測されなかった**。
一方で、これは「記事の質が同じ」ことを意味しない。new は最も短く（614字）、反論を独立した節にせず本文末尾に統合している。
それは構成の差であって、論証の強さの評価ではない。

**残る不確実性**：n=1、同一モデル、同一課題。E01–E23 の独立評価（複数課題・複数評価者）は未実施。
本物の回帰は、E05（因果監査）や E20（規範）のような、より判断の重い課題で出る可能性がある。

## 4. リスク4：検査への過信

### 4.1 方法

`scripts/selftest_consistency.py` が、リポジトリのコピーを作り、**1か所だけ関係を壊して**、
`check_consistency.py` が期待どおり失敗するかを確認する。

### 4.2 結果

| 変異 | 検出 |
|---|---|
| なし（control） | pass（exit 0） |
| 規則IDの欠番（R05→R99） | 検出（exit 1, "not contiguous"） |
| architecture の Phase 3.5 行を削除 | 検出（"architecture phase table differs"） |
| orchestration を「5役」に変更 | 検出（"five-role"） |
| evals から E12 を削除 | 検出（"not contiguous"） |
| UNIVERSAL-PROMPT.md を改変 | 検出（"stale"） |
| 禁止パターンの重複（P03→P02と同じ題） | 検出（"duplicate titles"） |

6つの変異すべてを検出し、無変異のコピーは通った。**検査は空回りしていない。**

### 4.3 限界

検査が保証するのは、**符号化した関係**だけである。

- 異なる言い回しの意味的な同値性。
- 参照が実際に読まれたか。
- ゲートが誠実に適用されたか。
- 記事の品質。

これらは [design-notes.md](design-notes.md) §3.4 に明記した。

## 5. 再現方法

当時のルーティング生データと A/B の出力はローカルの作業ディレクトリに置き、リポジトリにはコミットしていない。
測定に使ったスクリプトのうち、再利用できるものだけを `scripts/` に残した。

```bash
# 1. ルーティング（別セッションで description と依頼を渡し、JSON を保存）
python scripts/score_trigger.py decisions.json
python scripts/score_trigger.py decisions.json evals/trigger-prompts-heldout.json

# 2. 検査の変異テスト
python scripts/selftest_consistency.py

# 3. 通常のリポジトリ検査
python scripts/check_consistency.py
python scripts/check_repo.py
```

A/B の構造監査（`audit_ab.py`）は予備実験用の一時スクリプトだったため、リポジトリには残していない。
方法は §2・§3 に書いたとおりで、同じ課題と同じ仕様を用意すれば再実行できる。

## 6. 結論

| リスク | 状態 | 何が言えるか |
|---|---|---|
| 1. 取りこぼし | 部分的に検証 | 字面の推敲トリガーによる誤発火は new で消えた。heavy の recall 低下は観測されず、設計判断の1件は new が改善。ただし small-N・同一モデル |
| 2. 参照不読 | 構造は検証 | 参照なしでも5成果物と監査は通る。ただし品質は落ち、省略の開示が条件。old でも参照は1本しか読まれなかった |
| 3. ゲート遵守 | 1課題では退行なし | old/new/blind とも READY・Critical 0・構造6/6。品質と他課題は未測定 |
| 4. 検査の過信 | 反証可能 | 6変異を検出。意味のドリフトは検出できない |

**総合**：v3.1 の変更は、この検証の範囲では「壊れていない」。しかし「良くなった」とも言い切れない。
言えるのは、**発火の誤りは字面に依存し、参照は元々あまり読まれておらず、slim 化しても構造は通る**、という3点である。
品質の比較には、E01–E23 を独立評価者で回す必要がある。

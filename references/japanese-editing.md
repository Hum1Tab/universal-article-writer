# 日本語推敲エンジン：yomiyasu の7原則を記事執筆に組み込む

> 読むタイミング：Phase 4.2（推敲）、Phase 6（最終校正）。日本語の記事・論文・解説を書いた後、納品前に通す。
> この文書は [nanaism/yomiyasu](https://github.com/nanaism/yomiyasu)（MIT）の考え方を、記事執筆向けに要約し、実行手順に直したものである。原文のコピーではない。

---

## 0. なぜ必要か

AI が書いた日本語は、文法が正しくても読みにくいことがある。原因は、難しい単語よりも**文の構造**にある。

- 誰が何をしたのかが省略され、主語と述語が離れる。
- 道具や概念が、感情や意志を持っているように書かれる。
- 「壊れる」「効く」「溶かす」のような比喩動詞が、文字どおりの意味で使われる。
- 前置き、否定対比、太字、箇条書きが増え、情報密度が下がる。
- 文が長く、読点が多すぎる、または少なすぎる。

yomiyasu は、これらの**表層語彙ではなく構造**を直す。意味・主張・比重・言い切りの強さを変えずに、読み違えにくい文へ組み直す。

---

## 1. 最優先：意味の保持

書き換える前に、原文の次の4点を確認する。書き換えた後も、同じでなければならない。

1. **主張**：何を言っているか。論点を別の概念にすり替えない。
2. **比重**：何を重く、何を軽く扱っているか。否定していたものを並列にしない。比較の基準を変えない。
3. **言い切りの強さ**：断定・推量・可能性・許可・能力・義務・保証を変えない。「〜できる」を「〜する」にしない。「〜場合がある」を消して言い切らない。
4. **文の働き**：説明・評価・依頼・予定・伝聞・仮定・皮肉を変えない。伝聞を断定にしない。依頼を説明にしない。

**言い直しテスト（6点）**：書き換えの前後で、次が同じか比べる。

- 何について述べているか
- 何を認め、何を否定しているか
- 誰が誰にするか
- 範囲と条件
- 言い切りの強さ
- 数値・固有名詞・時期

1つでも変わるなら、原文を残す。判断できないときは、本文を変えず「書き手に確かめたい点」に回す。

---

## 2. 7つの変換原則

### 原則1：主述・修飾・条件を対応づける

- 主語と述語、修飾語と掛かる先、指示語と指す対象を対応させる。
- 条件・例外・否定・並列・数量・順序が、書き換えの前後で同じ範囲に掛かるか確認する。
- 主語や目的語を補うのは、原文・依頼・資料から確定できるときだけ。推測で足さない。
- 「〜は」「〜では」は文末まで掛かって読める。後半が別の主題の話なら、主体を勝手に足さず、書き手に確認する。
- 目的語を書かない他動詞の前に比較や条件の句が挟まる文は、前の名詞が目的語に読めないか確認する。

### 原則2：文の働きと文体を保つ

- 各文が、事実・評価・依頼・決定・予定・伝聞・仮定のどれかを記録する。
- 完了した変更を「〜します」にしない。現在の動作と今後の予定を混ぜない。
- 常体・敬体は、指定がなければ原文を保つ。技術記事だから敬体にする、という判断をしない。
- 文末を散らすこと自体を目的にしない。働きに合う文末を選ぶ。

### 原則3：擬人化を整理する

- 道具や概念に感情・意志を持たせた表現を直す。
- ただし、システムの客観的な動作（「このツールはログを集めます」）は残す。
- 人がした判断を、抽象名詞の作用のように書いている文は、誰の行動かが分かるときだけ人物の行動として書く。

### 原則4：比喩動詞を平易な言葉にする

- 「壊れる」「倒す」「効く」「溶かす」「潰す」などを、文脈に合う普通の動詞に直す。
- 比喩が持っていた含み（「うっかり」「ようやく」「地味に」）は残す。効き目だけをぼかした言い方にしない。
- データの「壊れる」は「おかしくなる」「使えなくなる」など、意味の幅が同じ言葉にする。時計や体の「壊れる」は残す。
- 慣用句（骨が折れる、手を焼く）は、AI っぽい比喩として扱わない。

### 原則5：前置きと否定対比の役割を確認する

- 「重要なのは」「本質は」が評価を担っているなら、評価を述語に移して残す。
- 前置きを削ってよいのは、削っても主張・比重が変わらないときだけ。
- 「AではなくB」は、誤解の訂正や見方の切り替えを担っているなら残す。単に言い換えているだけなら肯定文にする。
- 否定していたAを「Aに加えてB」に変えない。順位づけを変えない。

### 原則6：情報を足さない

- 原文・依頼・資料・会話・開いたファイル・コマンド出力にない主体・原因・条件・数値・感情・例を足さない。
- AI 自身の発言や一般知識を根拠にしない。
- 読めない語を、より狭い具体的な意味に決めつけない。
- 相対日付（昨日、先週）は、書いた日が確かなときだけ括弧で日付を添える。
- 書き手への指示や除外方針が本文に言い換えて残っているなら、読者向けの中身だけを残す。

### 原則7：文長・読点・装飾を整える

- 平均文長は30〜45文字を目安にする。長い文は、意味の切れ目で分ける。
- 1文の読点は0〜2個を目安にする。短い主題の直後に間を作るだけの読点は外す。並列を区切る読点、外すと掛かり先が変わる読点は残す。
- 太字は、本当に強調が必要な語だけに残す。見出し語とコロンの箇条書きは、値が短い事実なら残し、抽象的なラベルに長い説明が続くなら地の文にする。
- 絵文字、装飾的なダッシュ、文末コロン、表示されない太字を整理する。
- 箇条書きは、並列関係が明確で読みやすいなら残す。AI っぽく見えるという理由だけで地の文にしない。

## 3. 文書の種類と読者

yomiyasu は、文書の種類（12種類）と読者の知識（3段階）を決めてから直す。記事執筆では、主に次を使う。

| 種類 | 記事での例 | 直さない書き方 |
|---|---|---|
| `article` | 技術記事、解説 | なし |
| `paper` | 論文、研究レポート | 慎重な言い方、専門用語、「である」調 |
| `essay` | エッセイ、コラム | 読み取れる比喩、書き手の声 |
| `formal` | 仕様書、規程、政策文書 | 正式な漢語、「〜を行う」 |
| `promo` | 紹介記事、宣伝 | キャッチコピー、「！」、絵文字 |

読者の知識は `expert` / `informed` / `general` の3段階。`general` のときだけ、原文と資料にある説明で言い換える。説明がない語に説明を作らない。

## 4. 記事執筆への組み込み

### Phase 4.2（推敲）

1. 構造編集・段落編集・文編集・声の編集が終わった後、日本語の最終推敲としてこの7原則を通す。
2. まず**意味の保持**を確認する。数値、否定、主語と目的語、条件、言い切りの強さを変えていないか。
3. 次に、主述、比喩、擬人化、前置き、文長、読点、装飾を直す。
4. 直した箇所は `revision-log.md` に理由を残す。意味が変わりうる箇所は、本文を変えず「書き手に確かめたい点」に回す。

### Phase 6（最終校正）

- 本文だけを推敲し、`sources.csv` の書誌・数値・引用は触らない。
- 監査スクリプトの再実行前に、保存チェック（事実・数値・引用・hedge・`【未確認】`）を行う。
- yomiyasu の lint と diff が使える場合は、意味の変化候補を確認する。

### 実行例

```bash
# yomiyasu をインストール（任意）
npx skills add nanaism/yomiyasu

# 表現と書式の検査
python3 scripts/yomiyasu_lint.py article.md --doc-type article

# 推敲の前後を比較し、数値・否定・主客の入れ替えを確認
python3 scripts/yomiyasu_diff.py before.md after.md --fail-on=meaning-risk
```

`yomiyasu_lint.py` の候補は、直すべき指示ではない。文脈を読み、残すか直すかを決める。点数や候補数は、読みやすさの合否ではない。

---

## 5. やってはいけないこと

- 意味を変えて、読みやすくする。
- 主張を弱めたり強めたりする。
- 原文にない数値・主体・原因・感情を足す。
- 比喩を別の比喩に置き換える。
- 箇条書きを、AI っぽく見えるという理由だけで全部地の文にする。
- 文末を散らすために、文の働きを変える。
- 敬体・常体を、分野だけを理由に変える。
- lint の候補をゼロにするために、必要な強調や専門用語を削る。

## 6. 完了前チェック

- [ ] 主張・比重・言い切りの強さ・文の働きが、原文と同じか。
- [ ] 数値・固有名詞・時期・条件・否定が変わっていないか。
- [ ] 主語と述語、修飾語と掛かる先が対応しているか。
- [ ] 比喩動詞を、含みを残して言い換えたか。
- [ ] 擬人化を直したか。ただし客観的なシステム動作は残したか。
- [ ] 前置きを削っても主張が変わらないか。
- [ ] 原文にない情報を足していないか。
- [ ] 平均文長30〜45文字、読点0〜2個を目安にしたか。
- [ ] 太字・箇条書き・ダッシュ・絵文字を整理したか。
- [ ] 直した理由を `revision-log.md` に残したか。
- [ ] 判断できない箇所を、本文ではなく「書き手に確かめたい点」に回したか。
